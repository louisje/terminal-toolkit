# Development documentation workflow

## Purpose

開發文件是持續演進的工作工具，而非歷史流水帳。文件應即時反映實際開發狀態，協助規劃、設計、實作、驗證與跨對話交接。Git 保存歷史，因此可主動淘汰過時內容（rolling pruning），不必為追溯而保留失效資訊。

## Responsibilities

| 文件 | 比喻 | 責任 |
| --- | --- | --- |
| `ROADMAP.md` | 牆上的白板 | 未來規劃、待辦、優先順序、研究及暫緩事項 |
| `NOTE.md` | 手邊的筆記 | 正在進行及最近完成的工作、進度、下一步、阻礙與交接 |
| `docs/` | 抽屜中的文件 | 持久化設計、架構、介面契約、決策理由、限制及有長期價值的驗證結論 |
| Git | 歷史檔案 | 版本、實際變更與歷史追溯 |

ROADMAP 聚焦尚未完成的需求，不保存已完成事項的流水帳。NOTE 是滾動更新的工作現況，不是永久索引或 changelog。docs 可在設計階段建立，不必等到實作完成；應隨設計與程式碼演進，清楚區分提案與已實作行為。長期技術知識不應只存在 NOTE 或對話中。

## Development lifecycle

| 階段 | ROADMAP | NOTE | docs |
| --- | --- | --- | --- |
| 提出需求 | 記錄目標、範圍與待研究事項 | 視需要 | 複雜需求可先建立設計提案 |
| 啟動開發 | 標記已啟動並連結 NOTE，避免重複追蹤 | 建立當前工作、範圍及下一步 | 建立或更新相關設計 |
| 實作與驗證 | 更新仍未完成的規劃 | 即時更新進度、測試、阻礙及下一步 | 同步更新契約、決策與實際行為 |
| 中斷或交接 | 保留未完成需求 | 留下可執行的接續資訊 | 保留接手所需技術依據 |
| 完成與驗收 | 移除已完成事項；保留衍生待辦 | 移至近期完成，註明驗證程度 | 更新最終設計及持久化驗證結論 |
| 後續維護 | 新增尚未完成的需求 | 淘汰不再有工作價值的內容 | 修正過時描述與失效決策 |

此流程不是單向移動文件。開發期間可反覆參照設計、調整規劃及更新筆記；小型修改不必為了形式而建立新文件。

## Maintenance principles

- 即時性：在有意義的開發節點同步更新文件，不延至整個功能結束才補寫。
- 真實性：區分規劃、實作中、已實作、已測試、已提交、已部署及已驗收；未驗證事項不可宣稱完成。
- 一致性：每項資訊有主要維護位置；其他文件以簡短摘要及連結引用。設計契約以相關 docs 為主，工作狀態以 NOTE 為主，未來需求以 ROADMAP 為主。
- 滾動淘汰：移除已完成、已取代、失效或不再有工作價值的內容；尚有價值的技術結論移入適當設計文件。Git 保存已提交的歷史，不應在刪除尚未保存的重要資訊時假設 Git 已有備份。
- 可接續性：文件應足以讓沒有前一段對話記憶的開發者接手，並以程式碼及 Git 狀態核對真實現況。

## Handoff and resume

開始或接續開發時，先讀 NOTE、ROADMAP 的相關項目及必要設計文件，檢查 Git 狀態、近期提交與實際程式碼；若文件與實作不符，先釐清差異再繼續。

中斷前，NOTE 應按需要記載：目標與範圍、已完成及未完成事項、目前分支或提交、尚未提交的變更、最近驗證結果、阻礙、下一個具體動作及設計文件連結。若有背景執行或需人工操作，記錄可用的識別碼、查詢方式及必要前提；不要假設程序在重啟後仍存在。

NOTE 建議使用 In Progress、Recently Completed、Known Issues；無內容的區段可省略。保留期限以是否仍有助於當前開發為準，而非固定天數或筆數。

## Completion and review

提交或交接前，確認相關文件與程式碼一致，測試及驗收狀態如實記載，ROADMAP 已完成項目已清理，NOTE 下一步明確，docs 已保存必要的設計及限制。未完成的驗證或阻礙必須明確標示，不應為了收尾而宣稱完成。提交依使用者授權及專案慣例進行。

## Agent entrypoints

`AGENTS.md` 應作為跨 Agent 的精簡開發指引，引用本文件而非複製完整流程；`CLAUDE.md` 可作為 Claude Code 專屬入口並引用共同規範。Agent 不應假設所有客戶端都會自動載入這些檔案。此文件是開發文件維護流程的主要來源；日後調整流程時優先修改此處。
